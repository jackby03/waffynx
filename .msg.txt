feat(api): sites CRUD that actually applies, with atomic persistence

Fase 4 de SPEC-003, mas la tarea 3.2 (persistencia atomica) que vivia aqui.

Endpoints:

  GET    /api/v1/sites            autenticado
  GET    /api/v1/sites/{host}     autenticado
  POST   /api/v1/sites            requireAdmin
  PUT    /api/v1/sites/{host}     requireAdmin
  DELETE /api/v1/sites/{host}     requireAdmin

Leer la topologia lo puede hacer cualquier usuario autenticado; cambiarla
reconfigura lo que el proxy sirve, asi que exige admin.

El orden de commitSites es el contrato: se aplica al proxy y solo despues se
persiste. Una topologia que nginx rechaza no puede llegar al disco, porque un
reinicio la resucitaria. Y si la escritura falla despues de aplicar, se
re-aplica la topologia anterior para que runtime y disco coincidan.

mergeSitesIntoConfig reescribe solo la clave sites: del documento, asi que
las demas claves sobreviven aunque el operador edite el YAML a mano. El
resultado se valida con config.Parse, la misma implementacion que usa el
loader: si parsea, es seguro renderizarlo.

writeFileAtomic usa fichero temporal + rename y 0600 desde la creacion, porque
el config lleva el secreto JWT.

Decision de arquitectura: el API no es dueno del proceso nginx, asi que no
puede senalizar un hijo como hace el Engine. Usa `nginx -s reload`, que senala
al master por su pid file. Por eso NginxValidator y NginxReloader se mueven de
internal/engine a internal/sites: una sola implementacion de "hablar con
nginx", reutilizada por el motor y por el API. El Engine conserva su propio
reloader porque el si posee el proceso.

Tambien: Applier ahora crea su directorio. Antes solo lo creaba el Engine, y
el camino del API fallaba con "cannot find the path" en el primer apply. El
directorio es del Applier por definicion.

Config: nginx.http_listen y nginx.tls_listen (:8080 / :8443) porque el
renderer necesita los listeners y antes vivian solo dentro de nginx.conf.

Tests (11 de API, con validador y reloader falsos para no depender de nginx):

- crear aplica Y persiste: fragmento escrito y validado, un reload, config
  con sites:, claves ajenas intactas, y visible por GET.
- crear rechaza host con inyeccion, upstream sin puerto, host vacio y TLS sin
  key: 400 y el fichero no se toca.
- duplicado: 409.
- nginx rechaza: 500 con el mensaje de nginx, config intacta, sin reload y sin
  fragmentos huerfanos. Es el fail-closed del spec.
- update reemplaza el upstream en el fragmento; renombrar por body da 400
  porque la URL mentiria.
- delete quita fragmento y clave del config; segundo delete da 404.
- RBAC: viewer lista pero no crea ni borra; sin token, 401.
- orden estable en el listado.

Mas tests de nginx.go: configuracion incompleta, ejecucion real de nginx -t
con un script falso, stderr de nginx propagado, y reload correcto y fallido
(estos con build tag !windows, typechequeados con GOOS=linux go vet).
