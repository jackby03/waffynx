feat(sites): transactional apply with rollback, and sites: in the config

Fases 2 y 3 de SPEC-003.

Fase 2 - apply.go:

El orden es write -> validate -> reload, con rollback en cualquier fallo. Un
proxy con una configuracion que no paso nginx -t es peor que un apply
fallido.

- Applier escribe los fragmentos con fichero temporal + rename por fichero,
  asi nginx nunca lee uno a medias, y a 0600.
- Valida DESPUES de escribir, no antes: 'nginx -t' tiene que leer el
  directorio de include real, si no valida otra cosa. Hay test que comprueba
  que el validador ve los ficheros ya en disco.
- Si la validacion falla: restaura el estado anterior byte a byte y NO
  recarga. El proxy se queda con lo que ya tenia.
- Si la recarga falla: restaura y reintenta la recarga, porque nginx puede
  haber cargado parcialmente. El error del rollback nunca se traga: se anexa
  al principal con %w.
- Un fichero cuyo contenido no cambia no se reescribe, para que un apply sea
  un no-op real y no genere ruido.
- Los fragmentos que ya no corresponden se borran.
- Mutex: los applies se serializan, un reload no puede dispararse a mitad de
  escritura de otro.
- Los nombres de fragmento se validan (sin separadores, sin .., con .conf):
  es defensa en profundidad, aunque Validate ya los genera seguros.

Fase 2.3 - Engine.ApplySites: validador real que ejecuta 'nginx -t -c
<config_path>/nginx.conf' y adaptador al Reload() existente. El validador
ignora el directorio que le pasa el Applier a proposito: nginx valida el
include horneado en su propio nginx.conf, y apuntarlo a otro sitio daria una
falsa sensacion de seguridad. Rechaza configurar sin nginx.config_path en
lugar de crear un directorio relativo por accidente.

Fase 3.1 - sites: en la configuracion:

- config.Config gana Sites []sites.Site, distinto de Routes (que sigue
  siendo del gateway congelado).
- config.Parse valida con sites.ValidateSet: una sola implementacion de las
  reglas para el loader, el API y el renderer. Un host con ';' se rechaza al
  cargar el fichero, no al renderizar.
- internal/sites no importa nada interno, asi que config -> sites no crea
  ciclo.

configs/waffynx.yaml documenta sites: comentado y con el motivo: el render y
el apply aun no estan cableados al arranque, y anadir un sitio ahi hoy
validaria pero no protegeria nada. Es justo la promesa falsa que este
proyecto intenta evitar.

Tests: 8 del Applier (exito, rollback por validacion, rollback por reload,
borrado de huerfanos, no-op cuando nada cambia, nombres que escapan, wiring,
serializacion), 4 de config (parseo, inyeccion, duplicados, puerto), y 3
Linux-only del Engine con un nginx falso y 'nginx -t' real via script. Los
Linux-only se typechequean con GOOS=linux go vet.

Cobertura: internal/sites 90.1% (baja de 94.5 por el codigo nuevo), config
100%, engine 81.2%, total 44.4% -> 45.3%.
